# Focus after history deletion

Deleting the current conversation or all history hid the confirmation controls without returning keyboard focus to the initiating button. Cancellation already restored focus. The deletion flow now remembers whether confirmation owned focus, waits for the operation and UI re-enabling, and returns focus to its initiating button if focus remains within confirmation or on the page body. If the user moved to another control while deletion was pending, that focus is retained. No new UI, preview cards or confirmation steps.

Two regression tests failed before the change. Three tests cover both successful deletion targets and the user moving focus during pending deletion. The first implementation passed unit tests but actual Chromium keyboard Enter tests showed body focus: disabling the pending confirmation button blurs it. That observation is preserved in history-deletion-focus-browser-initial.json, whose source hash identifies the intermediate implementation. The corrected implementation accounts for this native blur. Final actual Chromium evidence has the correct initiating button focused for both targets; it also retains the prior native IndexedDB reload/export checks. Browser/server closed, no page errors.

Validation: production build passed, 116 unit test files / 4249 tests passed; source lint with existing .scratch vendor artifacts excluded, TypeScript and Docker config passed. The unit suite emitted existing asynchronous rejection-handled warnings. Browser-source/probe hashes and native focus outcomes pass verify-history-deletion-focus-browser.py. This is an isolated source harness, not full native editor or all-browser/screen-reader certification. Historical storage reports remain bound to their original source hashes and are not rewritten for this later product change.
