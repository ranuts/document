# Context budget omits custom system prompt: actual CPU rejection

Current built agent-plugin-Du88OJyO.js, actual CPU Qwen3-0.6B GGUF, online/warm cache. The UI accepted a 1900-character custom system prompt (龘 repeated 1900 times; 5700 UTF-8 bytes), inside generation.ts's 2000-character limit. The user request was only “Reply with a brief greeting.” Existing runtime byte budgeting covers message history, while wllama.ts adds the system prompt later in toOpenAIMessages. This small user request was rejected by the actual provider context error path.

Captured UI: “This request is too long. Select a shorter passage or split the task.” No assistant reply or usage statistics appeared. Source document remained unchanged, no preview, no page errors. Undo/Redo snapshots also stayed unchanged; this is not edit-history acceptance. Browser closed. The short user request does not need shortening; guidance currently omits the actionable custom-system-prompt cause.

The initial harness incorrectly waited for an assistant message after rejection and timed out; its original report is preserved separately. The corrected probe records all assistant messages without waiting for nonexistent success. Both test runs use injected GPU initialization failure only to select the real CPU engine. This is not physical GPU failure, offline acceptance or exact token measurement. Raw provider token counts are not captured, so no numerical token-overhead claim is made.

Installed SDK inspection: WebLLM's public engine interface exposes completion and side-effecting forwardTokensAndSample, but no complete-message token counting API. The current wllama wrapper exposes createChatCompletion and delegates model template processing to native completion. Do not count tokens by sampling, approximate them from characters, or recreate a different conversation template and call that exact accounting. A correct longer-term budget needs the loaded tokenizer plus the same model template/system/schema and response reservation, or an appropriate SDK extension.

Next changes should address actionable guidance for system-prompt overflow and then accurate provider-level context budgeting. Reducing all messages to a smaller arbitrary byte cap would preserve this omission and unnecessarily remove usable context. Do not silently truncate custom instructions or user documents. Run verify-cpu-system-prompt-context-diagnostic.py for this captured rejection and probe identity. No product change or new full-suite claim in this evidence-only run.
