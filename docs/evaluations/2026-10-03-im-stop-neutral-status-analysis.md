# Intentional Stop is a status

The previous production UI displayed user-requested Stop with the red error treatment. Cancellation now emits a UI-only `status` turn, rendered as plain muted text. The existing Restore request action remains available, restores only the draft, and stays disabled while running or when the user has a new draft. Status rows do not offer document insertion and do not become getLastAnswer(). No preview, confirmation, or new control was introduced.

The controller handles both aborted run results and rejected calls with its own aborted signal as status. Native/direct and planning AbortError handling now uses status in both live turns and stored hostGuidance. Actual model errors, step-limit errors, and errored tool results retain the error role. The LLM message role protocol remains unchanged; hostGuidance validation and restoration accept the new status tag. Existing stored error records remain valid and are not reclassified by comparing translated text. Generic controller Stop visibility remains subject to the existing history retention behavior; this change does not add new generic chat-history records.

Cancellation regressions were observed failing under the prior error role. The status-specific assertions also failed before the status role was implemented. The focused 4-file suite passed 71 tests, including cancellation result/rejection, next send, native writing cancellation, canceled late writing restored in its original conversation, ordinary late failure, status storage roundtrip, and draft/answer separation. Independent review found no Critical or Important issue. Production build, root lint, and full 115-file / 4080-test suite passed. Converter PromiseRejectionHandledWarning messages predate this change.

Actual production GPU Qwen 1.7B streaming was stopped using the visible Stop control. The single status row had no error border or background, retained a partial answer, had no write action, and re-enabled input. Restoring the request left the user-message count unchanged and did not start generation. A subsequent new draft disabled Restore. The next real model request replied “Hello.” No page or visible errors or preview cards were recorded. Light desktop and dark narrow screenshots were visually inspected.

These browser checks use isolated Chromium and cached models. Physical mobile and assistive-technology behavior are not established by viewport screenshots. The native-writing cancellation and stored host status behavior are covered by the relevant existing test fixtures, not by a new native editor runtime probe in this change.

Actual CPU Qwen 0.6B also passed Stop before visible text, neutral status, request restoration without resending, and new-draft protection. After waiting for the existing CPU model-ready UI state, the next actual inference answered “Hello.” No page or visible errors or preview cards were recorded. This CPU probe does not establish partial-answer cancellation: the first long-reply probe timed out waiting for 100 visible characters and remains a failed diagnostic.

A second CPU diagnostic confirmed the status and recovery checks but sent the next request before background model reinitialization was ready. The request remained in the draft and no assistant reply appeared; the probe consequently failed. Source inspection shows the existing readiness gate restores an early request as a draft instead of automatically replaying it. The final probe explicitly waits for the existing CPU status, enabled Load control and model-loaded note before sending. This timing caveat is preserved in the diagnostic and is not represented as an immediate post-Stop send pass. All exact executed sources and report hashes are retained.
