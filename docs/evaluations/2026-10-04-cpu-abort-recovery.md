# CPU SDK abort type handling and recovery

The existing pnpm patch for @wllama/wllama 3.6.1 now normalizes signal.abort messages and raw stack values before string operations. Strings retain their existing message cleanup; objects with string message properties use that message, and unknown values use Wllama runtime aborted. The native Worker is terminated and queued/pending tasks reject immediately, before optional diagnostic logging. Fatal errors retain raw stack text instead of waiting for asynchronous symbolication; this avoids hanging the request if optional decoding fails. Optional logger exceptions are contained. The TypeScript source and both ESM/CJS runtime entries have the same handler change. No dependency version, model default or UI step changed; the lockfile changes only the existing patch identity.

Regression tests first produced six failures and six unhandled errors on string/object/unknown aborts with a non-string stack. After the fix, both module entries reject initialization, terminate the Worker and reject later tasks with the appropriate error. Existing Worker error/exit cases remain covered. Full build, 116 test files / 4210 tests and lint passed. Independent review found no Important issue.

Actual owned Chromium CPU Qwen3-0.6B chat is also tested. Once the real SDK posts a wllama.action request, the diagnostic dispatches one parent-side synthetic MessageEvent to that Worker with signal.abort and an object message plus null stack. This exercises the real SDK receiver and pending real inference request; it is not a native Worker-emitted abort, physical device loss, OOM or real failed download. The original action is still sent, and no model response or error result is substituted.

The request ends with the existing generic request error and Restore request action. The diagnostic records one injected event, one Worker terminate call, no assistant reply, no residual usage statistics and no page errors. Native Word text stays empty. Pressing the existing Load button then sending a new greeting produces a real Hello reply and still leaves the document unchanged. The verifier binds the report to executed driver SHA-256 and checks these observations. The error guidance is still generic; this fix does not claim CPU-specific reload guidance.

This repairs the reproduced handler defect for non-string abort data and prevents the observed string-operation failure in the controlled path. The payload of the earlier real WASM failure was not captured, so its exact cause and full recovery are not certified. The old negative evidence remains unchanged; its installed-dependency hash check naturally becomes stale after this patch. The browser uses a warm owned profile, network available, service workers blocked and default webllm selection with navigator.gpu unavailable, resulting in CPU fallback. General privacy, cold offline resource failure, devices, memory reclamation amounts, threaded cleanup completeness and automatic replay are outside this evidence. Empty-document Undo/Redo fields are ignored.
