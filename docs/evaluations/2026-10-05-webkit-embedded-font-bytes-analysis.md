# Runtime embedded ASCW3 bytes are complete

Exploratory fresh desktop WebKit 26.5 native Word probe, unchanged runtime d71a1e8, no model load or document mutation. The actual loaded runtime identifies ASCW3 at synthetic font-file index 282, NeedStyles 15. Its file has Id `100`, Status 0 and stream_index 0; actual `GetStreamIndex` and `AscFonts.getFontStream` are callable.

Reading that actual font stream yields 6,868 bytes with TrueType prefix 00 01 00 00. Browser SHA-256 is `35ff902a3b9c9254ce3c57d610dad9e57008b8a3351691c463bee775644c1e18`. Independently reading public/fonts/100 and decoding the first 32 XOR-obfuscated bytes produces the same length and hash. The runtime embedded stream therefore matches the decoded served font for this build. Page errors are empty and context/browser close normally. The retained driver shows the byte bounds and independent hash computation; no equality is inferred merely from names or lengths.

This strengthens the candidate of passing already-decoded embedded ASCW3 bytes to the conversion Worker instead of its URL. Current fontSources sends only `{fileName,url}` even for this synthetic loaded stream. A product implementation still needs bounded byte copying, fallback when the stream API/data is absent, explicit raw-byte handling without applying wire XOR again, meaningful worker/host tests, and native Save validation. Ordinary fonts and native-pointer streams must not be copied wholesale or treated as the special embedded stream. No code/default/cache changes or product fix are established by this evidence-only probe. It does not verify complete font coverage, layout, physical Safari/iOS, global disconnection or model quality.
