# 聊天回答写入文档与默认模型加载

## 原因与默认模型

截图中的 Ask/问答路径只生成文本，不提供模型工具。模型说“已经写入”不会触发编辑器执行。默认仍为 WebLLM 的 `Qwen3-1.7B-q4f16_1-MLC`（4-bit 量化），本轮不改为更重的 4B 模型。

此前只在权重命中缓存时自动加载；首次使用必须在设置中加载。用户本轮明确要求默认加载，现在打开助手即开始加载默认模型，包括首次下载。有缓存时复用缓存；设置仍可停止、重试或选择其他模型，WebGPU 不可用时不启动下载。

## 实现

每条助手回答提供“写入文档”按钮。点击明确授权一次写入，应用捕获当前 DOCX 光标/选区，调用 insert_text 并读回验证。无选区时插入，有选区时替换。写入为纯文本，不转换 Markdown 标记或保留富文本格式；整个回答作为写入内容，不使用模型猜测文章正文。

该路径不依赖模型原生工具调用；普通聊天本身仍不自动修改文档。输入区的编辑/改写/摘要/翻译任务继续使用已有提案确认流程。XLSX 使用编辑任务设置单元格，PPTX 直接修改仍未开放。

正在生成时不能点击写入；同一按钮在操作中锁定，已执行后不允许再次写入。执行前编辑器未就绪等错误可重试。已发送但未验证/验证失败时显示检查文档与必要时撤销指导，不显示已写入，也不自动重试。

本地模型提示词改为指向实际写入按钮，禁止虚构已执行的修改。

## 实际浏览器验证与额外修复

Chrome DevTools 在新建测试 DOCX 中验证回答确实进入文档，没有改动用户原有文档。首次发现正文中连续两个空格被 HTML 粘贴解析压成一个，严格读回因此失败。已定位 SDK 粘贴解析：文本节点父元素的 white-space 为 pre/pre-wrap 时保留空白。

textToHtml 对连续空格、缩进、制表符和行尾空格使用已转义的 pre-wrap span，保留普通文本原有输出形式。不放宽验证规则，不将空格替换成 NBSP。

随后独立 Chrome 测试使用隔离的会话和测试文档（该写入测试禁用 WebGPU，避免重新下载模型）：

- 包含连续空格与行尾双空格的文本写入，正文读回完全一致，按钮状态 verified/已写入。
- 选中整个测试文档后写入下一条回答，验证单次替换结果。
