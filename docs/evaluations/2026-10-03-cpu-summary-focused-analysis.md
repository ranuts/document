# CPU summary-specific prompt: no adoption

The CPU result does not justify adopting the candidate. It improves omission/length in some cases, but introduces a severe goods/value relationship error and conflates inspection authorization with shipment authorization. All twelve results were applied by existing guards, so successful application does not establish factual correctness.

## Scope and controls

The same six already-observed [GPU fixtures](2026-10-03-summary-focused-cases.json) were run once on the cached production CPU path, current messages followed by candidate messages. These are regression/comparison fixtures, not new independent held-out acceptance cases. The displayed engine identifies Qwen3 0.6B; SDK instrumentation records actual four-thread multithread CPU inference with cross-origin isolation. The candidate system is identical to the prior [GPU summary candidate](2026-10-03-summary-focused-analysis.md). There is no product prompt or default-model change.

The experiment modifies the served SDK createChatCompletion boundary and captures source/instruction, complete messages and serializable non-message request fields. The original built plugin and SDK bytes remain unchanged on disk. Callbacks and signal objects are not model-sampling controls and are not compared by object identity. The [verifier](verify-cpu-summary-focused.py) checks all twelve actual inference rows, matching source/instruction, schema, captured parameters, native text/Undo/Redo and absence of previews, recorded external requests and page errors. It does not judge semantics or independently hash model weights.

CPU controls are the current production settings: temperature 0.7, top_p 0.8 and max_tokens 512. The GPU comparison used temperature 0. This is not a controlled CPU-versus-GPU accuracy or speed ranking. One fixed-order sample per case does not establish reliability, thermal behavior, physical mobile support, offline startup, native Save/reopen or full-language coverage.

The value-as-destination result demonstrates the boundary of literal currency validation: it can check the numeric/currency pairing while failing to recognize what it describes. The earlier GPU polarity and changed-name failures remain separate unresolved problems. Do not respond by universally prohibiting legitimate summary omissions or by adding confirmation cards; neither meets the requested writing behavior.

## Harness correction and validation

The initial adaptation retained a six-message expectation from an older few-shot experiment even though this candidate has two messages. It recorded the first current row, then stopped with `Prompt variant did not execute`. The [diagnostic](2026-10-03-cpu-summary-focused-harness-diagnostic.json) remains failed and is not model-quality or complete-run evidence. The corrected probe expects the actual two-message pair; its hash matches the complete twelve-row report. Since CPU sampling is nonzero, initial and corrected generations can differ; reports are not overwritten to imply identical generations.

The complete report confirms twelve applied edits, each with exact native Undo/Redo, no preview and unchanged bundle bytes. Probe syntax, evidence verifier and repository lint passed; read-only review confirmed the relationship/date-role failures and the non-adoption decision. These are the relevant checks for this evidence-only turn; no product source or dependency changed, so a new build/full unit run is unnecessary. Existing overall quality and device acceptance gates remain open.

Reproduce: `WRITING_EXAMPLES_CASES=docs/evaluations/2026-10-03-summary-focused-cases.json WRITING_EXAMPLES_REPORT=<unique-path> node docs/evaluations/probe-cpu-summary-focused.mjs` against preview 5193, exclusively using the cached `.scratch/ai-offline/profile`. Each load/inference stage has an explicit bound. Do not run simultaneous probes with that profile. Artifacts: [probe](probe-cpu-summary-focused.mjs), [complete observations](2026-10-03-cpu-summary-focused.json), [verifier](verify-cpu-summary-focused.py).

## Next verification direction

[SummaC](https://arxiv.org/abs/2111.09525) studies the sentence/document granularity mismatch in NLI-based summary consistency checking and aggregates sentence-pair scores. Its reported benchmark result is not a guarantee for this app or these languages. [Task-taxonomy research](https://arxiv.org/abs/2402.12821) evaluates explicit factual-error types across multiple datasets; our proposed experiment should separately test person/object/date-role swaps, negation, conditions, attribution and unsupported causality rather than request one generic confidence score. This is an inference from the papers and our observed failures, not a verified product checker.

A possible independent local NLI baseline is [mDeBERTa's model card](https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-mnli-xnli), which describes multilingual pretraining and NLI training/evaluation on 15 languages and warns that transfer to others may perform worse. It does not prove browser runtime compatibility, resource budget, or Japanese/Korean/Portuguese document-summary accuracy. Before any integration, a separate experiment must establish real local execution, positive-control retention, detection of the retained wrong outputs, latency/memory and language-specific false refusals. Entailment alone also cannot establish requested omission, single-sentence style or retention of all requested facts. No validator dependency/model was installed or shipped in this turn.
