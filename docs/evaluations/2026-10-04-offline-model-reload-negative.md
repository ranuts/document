# Offline reload after model Worker disposal: negative result

This experiment advances beyond loaded-model offline chat. Both owned Chromium profiles first load a model online, set the context offline, change the provider away and back through the r-select component's public value/change API, wait for initial model Workers to close, then press Load again. The page remains open, service workers are blocked and the native editor stays mounted. CPU uses navigator.gpu unavailable with the default webllm provider, which selects the CPU fallback; it is not explicit wllama selection.

Neither final run reaches the Model loaded status within 180 seconds. GPU closes its first model Worker, then requests the WebLLM Worker script and wllama JavaScript while offline. CPU closes its five original blob Workers and creates five new ones, then requests wllama WASM three times. Its page errors include a WASM network failure and `t.replace is not a function`. The latter is an additional error-handling issue to investigate, not evidence of model text generation. No final row, reply, document snapshot or UI error snapshot is recorded after these timeouts, so they cannot establish the terminal interface state or unchanged document content.

The observed failure is scoped to a running page with service workers blocked, without diagnostic response interception. This does not prove the deployed PWA's resource cache fails. The next investigation must inspect the actual service-worker/asset caching path and repeat with its controller active. Model weight cache alone is insufficient evidence of offline reload when the Worker and WASM resources are unavailable. Earlier warm in-memory offline successes remain valid and are not cache-reload successes.

Two earlier diagnostic mistakes are preserved separately. The first used selectOption on a custom r-select, which fails before reload. The second required the unrelated native spell-check Worker to close and therefore aborted despite model Workers closing. Final drivers filter WebLLM script Workers or CPU blob Workers for the owned page and assert at least one initial model Worker. Earlier executed driver bytes are not separately retained; only final reports are bound to their final driver SHA-256. The negative verifier checks failures, relevant resource requests and lifecycle evidence without turning them into passing acceptance.

Provider inspection also corrected three earlier analyses: localStorage agent-panel-provider does not select the panel provider, which is constructed with webllm by default. Their actual CPU replies and SDK parameter capture remain valid; claims of explicit CPU selection were withdrawn in commit `9189e54`. The final drivers add selected-provider capture to a success row, but no such row was reached here. Provider selection therefore follows the exercised component API and source, not a successful final report field.

No product code changed. These reports do not certify cold offline launch, model cache eviction, privacy, physical devices, automatic recovery, or saved history. Attempted page requests are GET without bodies in this observation; that is not an exhaustive network audit.
