# App-independent WebKit offline-emulation failure

Local Playwright 1.62.1, desktop WebKit 26.5. Independent tiny owned loopback server, no product assets/editor/model/cache dependencies. Its service worker activates/claims and returns literal HTML for navigation without fetching or reading Cache API. Each disruption uses a fresh context/server, actual controller prerequisite, and explicit cleanup. The retained driver is independently authored; it is not a copied application handler.

With context.setOffline(true), navigation fails with the same `WebKit encountered an internal error`. With the owned origin stopped and the browser online flag unchanged, navigation returns status 200, response.fromServiceWorker true and exact LOCAL_LITERAL heading. Both contexts/browser/servers close. Thus the observed offline-emulation navigation failure can occur without any product cache or navigation code; it should not motivate an application-cache workaround. This does not prove physical Safari/disconnection behavior or explain the separate Home immediate-navigation worker-install stall.

Primary upstream corroboration inspected 2026-10-05: [Playwright issue 42775](https://github.com/microsoft/playwright/issues/42775) reports a similar literal-response failure in 1.63.0 and contrasts offline emulation with stopped-origin controls. Our local version differs, so the local reproduction—not an assumed release fix—is the authoritative evidence here. The report is user-supplied issue evidence, not proof that a fix ships in the installed package. No dependency update, product modification, external issue submission, full-offline acceptance or new product unit suite/build is claimed. Original native failures remain retained with their narrower testing limitation clarified.
