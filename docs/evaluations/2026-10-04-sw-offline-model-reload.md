# Offline model reload with the application Service Worker

Following the SW-blocked negative result, both owned Chromium profiles now allow service workers and visit the landing page online before opening a new Word editor. The actual initial and final controller URLs are recorded as `/sw.js?isolation=1`. The preview server config sets COOP/COEP headers for development and preview, so isolation is expected in this local environment. The earlier attribution solely to inherited diagnostic profile state was incomplete. This run does not inject response headers, but it is not evidence for a nonisolated hosting environment or default deployed headers.

After initial model load, the browser context is set offline. The r-select component's public value/change API changes provider away and back to webllm, causing disposal; this is an API-driven control change, not a keyboard or pointer selection acceptance test. The driver waits for all initial model Workers to close before pressing Load. GPU closes its initial WebLLM Worker and creates one fresh Worker; CPU closes five initial blob Workers and creates five fresh ones. CPU retains webllm selection with navigator.gpu unavailable, so its actual engine is the CPU fallback.

Both models reach Model loaded again and produce Hello through visible IM chat while navigator.onLine=false. The complete native Word text stays empty and no recorded page/message errors or preview cards occur. GPU captures one real streaming request; the inherited GPU interceptor does not capture CPU options. The verifier checks model Worker close/create ordering, actual engine, controller, offline state and full text snapshots, and binds final reports to executed driver SHA-256.

The application build stamps JS/CSS/WASM into APP_ASSETS_TO_CACHE, and the application SW has offline cache fallback. The positive run supports offline in-page model reload under the observed SW controller; it does not individually hash every consumed cache response or prove a specific cache body was used. Combined with the SW-blocked failures, the next investigation should distinguish page launch, controller mode and cache lifecycle. No product change was required for this observed controller variant.

The first SW-enabled attempts timed out at controller recognition because the diagnostic required scriptURL to end with `/sw.js`; the actual successful runs record `?isolation=1`. Their failed reports are preserved as before files. Prior executed driver bytes are not retained separately. Final checks use URL pathname and record the controller URL.

Scope: same already-open page, warm persistent profiles, app/model loaded online beforehand, offline model disposal/reload and one English greeting. It does not establish cold offline application launch, complete process restart, ordinary SW mode, cache eviction, update migration, physical devices, writing/tool quality, resource budgets or general privacy. SW headers inherited by this variant may affect isolation and CPU threading; those values were not independently recorded. The earlier SW-blocked negatives remain unchanged. Empty-document Undo/Redo fields are ignored.
