# Draft preservation during CPU Stop recovery

Current native Word IM loaded actual Qwen3 0.6B automatic CPU fallback in warmed desktop Chromium. GPU availability alone was forced off. The UI max-token setting was changed to 1024 and a long story request generated real streaming content. After clicking the normal Stop control, one diagnostic SDK load wrapper held the next model reload before delegating to its unchanged original loader. This created a reproducible recovery interval; inference outputs and host document operations were not substituted.

During that interval the editable input accepted “为什么旧钟会走慢？”. Pressing Enter left the draft intact, Send disabled, user-message count at one and actual SDK generation count at one. Releasing the gate completed actual model reload. The same draft remained, Send became enabled and generation/user-message counts were still one: nothing was queued or auto-sent. Only the subsequent explicit Enter cleared the draft, added the second user message and invoked generation a second time.

The document stayed exactly its empty paragraph, with no error guidance, preview cards or recorded page errors. The [raw report](2026-10-05-stop-recovery-draft.json) binds the executed [driver](probe-stop-recovery-draft.mjs) and current plugin hashes. SDK counter wrappers delegate to original implementations. `partialText` is UI row text and includes action-control labeling; it is not a pure model completion and is not used to assess answer quality. The [verifier](verify-stop-recovery-draft.py) checks the exact draft, availability transitions, counts before/after deliberate submission, unchanged document and browser closure. The process ended with exit 0.

This establishes this current desktop CPU recovery/draft route, including an Enter attempt while loading. It does not certify naturally slow/failing reloads, every conversation/model/language, physical devices, offline/PWA, Save/reopen, network privacy or semantic response quality. No measured latency claim is made. The application behavior already met this requirement, so no product change or automatic sending queue is introduced.
