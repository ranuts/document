# Actual chat after going offline

Product after `f147c84` was exercised in two independent owned Chromium profiles: GPU Qwen3-1.7B and CPU Qwen3-0.6B with navigator.gpu unavailable. In each case the editor and model load while network is available. Only after the model-loaded status does the driver call context.setOffline(true), verify navigator.onLine=false, change generation settings through the UI, and send a new greeting request.

Both actual local models complete a Hello reply with visible generation statistics while offline. The entire empty Word document remains unchanged. No page errors, visible message errors or preview cards occur. A page request listener installed before navigation records zero request events during the offline phase. This is an observation of page request events, not an exhaustive network audit of every browser/Worker transport or proof of general privacy compliance. The browser context's offline setting and successful generation establish independence from a live cloud response for these samples.

The GPU report also captures one real streaming Worker request with the entered generation parameters and greeting. The inherited GPU-specific interceptor does not observe the CPU SDK; CPU inputs=[] is expected and not parameter-capture evidence. The separate CPU SDK forwarding experiment remains the relevant parameter evidence. Drivers and unmodified reports are bound by SHA-256 in verify-warm-offline-chat.py.

This verifies warm, already-loaded-model inference after a network transition. It does not establish cold offline navigation, reload from cached model artifacts, cache eviction behavior, PWA installation, real Safari/iOS/Android/Windows compatibility, saved-history restoration, writing/tool-task fidelity or deployed CSP/privacy acceptance. Service workers are blocked; these runs therefore are not PWA offline-launch tests. Inherited empty-document Undo/Redo snapshots are ignored. No product code, model default or experimental response headers changed.

Correction after provider-control inspection: setting localStorage agent-panel-provider does not select the runtime provider; the panel constructs its selector with webllm by default. Earlier wording claiming explicit wllama selection was incorrect. Raw reports and executed drivers are preserved; actual CPU engine/reply observations remain valid. The offline-model-reload follow-up records the selected provider directly.
