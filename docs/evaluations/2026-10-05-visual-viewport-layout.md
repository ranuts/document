# Composer layout follows actual panel height

Product baseline `577a4c8`. An actual Chromium/native Word IM run supplied synthetic VisualViewport geometry while leaving the layout viewport at 390×900. With panel height 400/top80 or 300/top100, settings closed/open, the baseline overflowed: the send bottom exceeded the panel bottom in three of four cases. Raw before geometry is retained; the browser closed without errors. This reproduced a CSS boundary gap, not a natural physical-keyboard event.

The compact layout previously used a layout-height media query. It now uses a named size container on the explicitly sized panel, so compact descendants follow the height updated by the VisualViewport helper. [MDN container-type](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/container-type) describes size query containment. No duplicate JS compact state or extra UI was added.

The identical synthetic geometry run after the CSS repair passed all four cases: input and send stayed inside the visual region, Chinese draft text remained, and there were no browser errors. The 300px/settings screenshot was inspected. Independent source review found no important containment or selector issue. Production build and whitespace checks passed; the build retained its large-chunk advisory. Ordinary layout regression at 1280×900, 390×900, 390×400 and 320×400 verified no horizontal overflow, visible input and 44×44 narrow-screen primary targets. The 390px settings pane had no horizontal overflow.

`verify-im-visual-viewport.py` checks the matched before/after geometry and failure-to-pass transition. `probe-im-visual-viewport.mjs` is the ad-hoc driver copied after execution; this is not preregistered model evaluation. Real iOS/Android keyboard behavior, browser address-bar transitions, natural back-forward-cache admission and physical mobile inference remain unverified. This fix establishes actual DOM/CSS behavior under controlled viewport events only.
