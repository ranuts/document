# Worker CSP: automatic cache upgrade and fresh-process offline check

The current build automatically caches the new Worker URL with its response CSP, and a fresh offline Chromium process runs the actual default GPU model under that cached policy. No Worker response body or cache header was manually repaired in this experiment.

The existing GPU profile initially held two exact old Worker responses (`webllm.worker-BX0TIRUM.js`), both without CSP. Their SHA-256 is `1248840615c89e1bedc0ad3fbcb0b78fa7963defdc5c14e0e65733a5a030dfe5`, matching preceding baseline records. The new Worker URL was initially absent. The online application then populated both current core/runtime cache entries for `webllm.worker-CMk6FPDh.js` with the exact policy and built SHA-256 `663218a9e1fa6790319dd16308de55c2eb7fbc329f2b379101de2cec7a0de8ba`. Old runtime entries may remain; the new application requests the distinct new URL.

The first run stopped at an overly strict probe guard accepting only a controller URL ending `/sw.js`; the actual own controller was `/sw.js?isolation=1`. Its uncached request already failed offline, and its online cache snapshots establish the observed old-to-new cache transition. This is a harness failure, not an application offline failure. The complete diagnostic report is retained as `2026-10-03-worker-csp-offline-controller-diagnostic.json`; it does not establish cold inference or policy execution.

The corrected probe accepts only the same-origin exact `/sw.js` path with no query or exact `?isolation=1`. The second run retains the already upgraded cache, warms current application state, closes the entire persistent browser context, and starts a new process with offline emulation and an unreachable HTTP proxy with loopback bypass disabled. An uncached same-origin fetch fails and the own Worker controls the editor. Actual displayed engine is WebGPU/Qwen3-1.7B, actual Worker URL is the new hash, and its policy fingerprint exactly matches all current-URL cached CSP/header/body checks.

To avoid the earlier debugger evaluation pitfall, a CDP session attaches to the actual native Worker and evaluates the control with `allowUnsafeEvalBlockedByCSP:false`. The result is an EvalError explicitly identifying CSP's lack of unsafe-eval. This is explicitly CSP-respecting debugger evaluation, not the ordinary-timer control used in the preceding online experiment. No diagnostic code is appended to the Worker response in this run. The real cached model then returns `Hello.`, with no visible inference errors or main page errors.

Evidence: `2026-10-03-worker-csp-offline.json`. Scope is desktop isolated Chromium/Metal, default cached model, current local preview configuration and one cold-process conversation. It does not prove every GPU model's new-policy offline startup, CPU Worker policy, fresh artifact redirects, cache eviction, deployed Pages/Docker upgrade, Safari/iOS/Windows, physical network removal or device reboot. It also does not retroactively upgrade a running old Worker/old cached app shell. No semantic writing-quality or Save/reopen claim.

The old preview on port 5193 was verified to lack CSP and then restarted with the current configuration, retaining the profile's model/cache origin. A synthetic blank cache-inspection page is served by a route only at `/__cache_probe__.html`; all actual application, Worker and Service Worker responses are untouched. No product code or generated bundle changed in this turn.

Reproduce with `node docs/evaluations/probe-worker-csp-offline.mjs` while the current-config preview runs at 5193 and the cached GPU profile is unused. A later rerun on this profile cannot reproduce the original pre-upgrade cache state; its first snapshot will already contain new entries. The retained diagnostic records the actual initial state, not a reconstructed one.

`python3 docs/evaluations/verify-worker-csp-offline.py` verifies both report roles, prior no-policy cache and initial new-URL absence, automatic new response caching, exact hash/policy, actual native model/Worker, offline control, CSP-respecting eval failure and successful reply. Syntax and repository lint also pass. Production source is unchanged, so no new build/full product test rerun is claimed; those checks from the implementation belong to commit 238da46.
