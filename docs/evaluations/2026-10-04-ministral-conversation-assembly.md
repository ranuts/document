# Ministral conversation assembly: unresolved placeholder observed

The installed SDK's actual `getConversationFromChatCompletionRequest` is exposed through an appended diagnostic export in a scratch copy. It consumes recorded Worker requests from the six-case Ministral run plus the separately fetched official MLC config in the catalog audit. Each includes its final user message and appends the SDK assistant reply header, as the inference path does before first prefill. No source rewriting of the assembly algorithm or product changes.

All six resulting arrays are exactly: system wrapper + supplied system message + `[/SYSTEM_PROMPT]{function_string}`, one `[INST]...[/INST]` user message, and an empty assistant header. System prefix token IDs are `[1]` separately, as used by initial prefill. The user source/instruction JSON appears once; neither system/user wrapper is duplicated. However, the function placeholder remains literal even though no function calling is requested and the config's function string is empty.

Source explains this reconstruction: `Conversation.getPromptArrayInternal` replaces the system-message placeholder but not the function placeholder in `system_template`. Function substitution occurs in a different message-processing branch when function calling is enabled. This mismatch is a concrete investigation lead. It is not yet established as the cause of writing degeneration, and changing tokenizer or defaults would be premature. Next experiment should remove only this placeholder from fetched config while preserving model, requests and generation/validation settings.

The verifier binds SDK/diagnostic module/baseline/config record hashes and independently asserts every exact reconstructed prompt. This is direct SDK execution in Node, not capture of browser-internal GPU prefill tokens. The inference run's consumed cached config bytes/revision were not retained, so correspondence with those exact runtime prompts remains inferred from the recorded config and code. No compiled weight/template compatibility, semantic quality, device/offline/privacy or deployment certification.
