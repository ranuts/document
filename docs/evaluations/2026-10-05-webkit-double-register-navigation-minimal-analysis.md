# App-independent reproduction of installing/pending state

Independent tiny loopback pages/service worker, desktop WebKit 26.5, no product/editor/model code. Extends 693bb9c's unawaited first registration: the destination now also registers the same root-scope worker and records its promise state. Each case uses a fresh context/server; browser/context/server cleanup completes.

Immediate navigation before first register settles, followed by second register: only bootstrap marker arrives, second promise remains pending after the five-second controller observation, registration shows installing, controller null and caches empty. This matches the measured product symptom more closely than the prior no-second-register case, which had no registration. The controlled case waits for Home control before navigation, then registers again; all markers arrive, the second promise resolves with activated worker, controller and tiny cache present.

Combined with product timeline 9872dd7 and the prior server/event diagnostics, this establishes an application-independent registration/navigation race reproduction for the local installed WebKit. It does not prove permanent deadlock, internal engine cause, physical Safari or other versions. The five-second minimal observation is not a 60-second measurement; longer product observations are separate retained runs. The controlled case waits for full control, so whether merely awaiting registration settlement is sufficient with a second registration still needs an explicit test.

This evidence now supports exploring a bounded lifecycle handoff before leaving Home, or a browser-specific recovery, without attributing the stall to model/converter/cache resources. Removing Home caching, blocking Open indefinitely, arbitrary retries or claiming complete offline support would be misaligned. No product modification, external issue submission, build/suite, global offline/privacy or semantic acceptance is established by this diagnostic.
