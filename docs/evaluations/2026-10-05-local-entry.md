# Browser IM entry dependency boundary

The browser previously dynamically imported the public agent-plugin barrel, which re-exports the shared LLM provider API. Both app initialization and sidebar toggle now import a dedicated `agent-plugin.ts` entry exporting only the existing `createAgentPanel` and `toggleAgentPanel` from the same panel module. The shared/public barrel remains available unchanged. Lazy loading, singleton panel state and its component registrations are preserved.

A Vite generateBundle/module-graph audit was run before and after the source change in separate scratch output directories with public copying disabled. Before: 102 parsed cloud-provider/Anthropic SDK modules, **0 rendered cloud-module bytes**. After: 0 such parsed modules. The original cloud code was already tree-shaken out, so this is not a demonstrated runtime cloud capability or data-upload fix. Final written-file hashes and lengths were checked separately from generateBundle snapshots, which precede Vite rewrite/worker output steps. The diagnostic agent chunk changed from 179,171 to 179,179 bytes; total emitted JS changed from 13,542,617 to 13,542,602 bytes. These tiny differences do not establish a meaningful download saving or performance improvement. The useful result is removal of unrelated provider parsing from the product entry graph. Production build no longer emitted the prior Anthropic node:fs/node:path browser-externalization warnings; the unrelated large-chunk warning remains.

Validation: 129 files / 4413 tests, TypeScript, targeted lint, production build and independent read-only entry review passed. A fresh headed Chromium 151 native installed-PWA run against the new production build seeded a self-hosted CPU model and PPT editor, closed the browser, shut down the entire serving origin, confirmed independent fetch failure, and restarted the installed app. Sidebar toggle and automatic stored CPU/provider URL restoration worked without offline settings re-entry. An actual greeting, bounded IM slide/text commands, native Undo/Redo, Save download and actual local-file reopen all completed. The saved 36,499-byte PPTX hash was `ff95125e2ad61868df4d20660043f0c50d912f3a1e6778e9a27b6f0de037a606`; reopened slide/text structure matched exactly. No IM errors/previews were observed. The test installation/context were cleaned up and owned server stayed closed.

The build audit covers selected cloud provider modules in the app graph, not every potential network capability in every library or process. It does not replace privacy/network verification. The browser run covers CPU, a bounded PPT command sequence and Save download fallback; it does not certify GPU, all model quality, native OS picker, mobile, physical network isolation/OS reboot, deployment policy or all document operations. Those acceptance gaps remain open.
