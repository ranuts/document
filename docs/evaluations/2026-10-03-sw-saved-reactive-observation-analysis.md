# Event observation isolates landing prefetch interference

The two current [prefetch-on](2026-10-03-sw-saved-reactive-prefetch-on.json) and [prefetch-off](2026-10-03-sw-saved-reactive-prefetch-off.json) runs share the same probe/driver hashes, real build artifacts and native old Word edit/save checkpoint. The first landing VERSION query waits reactively for controllerchange, bounded at 55 seconds. There is no fixed sleep or outgoing-Worker polling during that wait. An init-script listener also records controllerchange events that precede the wait so they are not missed. The product updater is unchanged.

With normal prefetch enabled, the event wait times out at 55,006 ms, and the subsequent VERSION observations still show the old vendor with the correct installed waiting candidate and zero editor windows. With the existing prefetcher stopped before its landing DOMContentLoaded handler, controllerchange arrives 6 ms after the observer begins; the subsequent VERSION query confirms the real candidate. This is not a six-millisecond total save-to-upgrade measurement. No prefetch fetch is recorded within the disabled observation interval. Neither run clears caches, terminates Workers or makes manual promotion calls.

The off run reopens the old saved marker exactly and completes candidate native Undo/Redo/Save/reopen and same-context offline/CSP controls. Both reports retain passed=false and completeMigrationPassed=false because the base probe's broad gate requires three document types, while these diagnostics run Word only. The on run has a migration error; the off run has no report/page errors and its Word rows complete. The verifier checks the individual outcomes without turning diagnostic intervention into production acceptance.

Together these observations show the fixed quiet interval is unnecessary for this successful diagnostic and that outgoing-Worker query polling is not sufficient to explain the enabled-prefetch failure. They justify coordinating prefetch with a pending update; they do not identify a Chromium internal request defect or prove that every browser/device shares it.

## Product change and verification boundaries

`public/landing-prefetch.js` now watches the active registration before warming. A pending application /sw.js install or waiting version pauses warming and cancels the current abort signal. The pause is independent of page-leaving state, so user activity cannot restart old-version warming. Controllerchange or failed/redundant installation resumes warming. The unrelated native empty stub Worker does not block it.

Paused hover/focus intents are retained and replayed after upgrade, including 3G where background warming is deliberately disabled. Request-map generations prevent an old aborted chain from clearing the new build's deduplication state. Page-leaving still prevents resume; back/forward restoration can resume afterward. Waiting for an update may keep speculative warming paused while another editor prevents promotion; actual document opening and existing offline caches are retained. No fixed delay, additional UI, vendor CSP shipment or cloud behavior is introduced.

Eight new focused unit cases cover pending waits, updatefound cancellation, failed installs, foreign stub exclusion, 3G intent recovery, initial waiting-to-redundant recovery, a cancelled response stream and an unload/controllerchange race. The first pending-install/wait tests and the review-discovered recovery cases failed against their preceding implementation before the corresponding fixes. Independent review found no remaining Critical/Important issues; its two concrete coverage limitations were then exercised by the stream/unload cases.

The reviewed product build succeeds. All 116 unit files / 4,183 tests pass; the suite still emits an existing asynchronous-rejection warning outside this scoped change. The four existing isolated Chromium landing-prefetch E2Es pass, including all three editor engines, cold-open font checks and core cache reuse. Scoped reactive evidence verification and lint pass. These checks do **not** replace the next required real two-build, three-type saved-session migration run against the new product logic. The native CSP experiment remains unshipped, and semantic model-quality, deployed delivery and physical-device gates remain open.

Run `python3 docs/evaluations/verify-sw-saved-reactive-observation.py` for the retained diagnostic pair. Use a unique TWO_BUILD_REPORT with the reactive driver; REACTIVE_STOP_PREFETCH=1 is explicitly diagnostic and must never be described as production behavior.
