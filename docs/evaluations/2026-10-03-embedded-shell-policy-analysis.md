# Embedded editor cached-shell response policy fallback

## Product change and boundary

`public/sw.js` now selects delivery policy from either the existing `isolation=1` script URL or the current build's own `/editor.html` response in `CORE_CACHE`. Both COOP `same-origin` and COEP `require-corp` must be present. This covers a COEP editor embedded under a nonisolated parent, whose actual isolation capability is false and whose app registration still uses the plain Worker URL.

The lookup is confined to this exact build's core cache and static shell URL; provider/model caches cannot enable the policy. It ignores Vary when reading the static shell, whose bytes do not differ by request Origin. Concurrent readers share one lookup. Positive results are retained, while missing entries, ordinary headers and storage errors clear the result so a later response can retry. Response delivery remains streamed; original cache content is not rewritten. Status-zero errors and normal hosting continue to pass through. CPU thread selection is unchanged and still uses actual isolation capability.

No UI controls or global hosting headers were added. This is a delivery fallback under the current Worker, **not a complete first-old-controller upgrade fix**.

## Native browser evidence

`probe-isolated-cross-origin-embed-fixed.mjs` extends the preceding protocol-based cross-origin embed control. It uses real HTTP proxy hosting and actual Worker registration. The parent and embedded document remain nonisolated; the Worker URL remains plain `/sw.js`.

The old-controller initial request can still be blocked before the new Worker takes over. The final report explicitly records `firstUpgradeCompatible:false`. The runtime-cache vendor hash is unchanged, so the app's existing controller-change rule does not automatically reload this failed iframe. No first-upgrade recovery is claimed.

After verifying that the new Worker controls the document and the current core shell has COOP/COEP, the test deliberately removes only the stored native iframe response's COOP/COEP headers. It verifies all 122,834 bytes are identical before and after that metadata change. It then reloads the same parent with the same supported `document:open-buffer` fixture. The **product Worker** delivers the missing policy; the native document and full API load. The stored iframe response still has no COEP afterwards, demonstrating delivery repair instead of test-side header repair. The native fixture is the DOCX generated by the earlier cold Save probe.

Final `passed` requires the successful ordinary embed control, native readiness after stale-response reload, unchanged fixture bytes, policy on the current core shell, actual current Worker version, a nonisolated parent/embedded capability and no page errors. The initial blocked request is retained in the failure log rather than hidden.

The proxy's static shell reports `Vary: Origin`. The final reader records matching with and without `ignoreVary`, so this evidence does not infer a cache miss merely from the presence of Vary.

## Diagnostic controls and harness corrections

Initial candidate and intermediate reports are retained. A diagnostic reader incorrectly treated `Locator.evaluate`'s first argument as the supplied version string; it is actually the body element. That queried/created an invalid cache name and made the shell appear missing. Another initial reader used `version` instead of the Worker protocol's `cacheVersion` reply field. Neither diagnostic is evidence that the actual current core cache was missing. Both readers are corrected in the final source.

These harness errors are separate from the real negative-memo regression, which was independently reproduced by two same-Worker source-based tests. The final browser result also separates initial old-controller failure from successful current-Worker delivery.

## Remaining integration work

Before enabling global acceleration headers, select/wait for the policy-required Worker before the first native iframe request in the embedded upgrade path. This must preserve current document edits and the host's embed protocol; it cannot be replaced by unconditional reloads or a passing second-open test. The broader device/model-quality/deployed-hosting requirements remain active. This evaluation is Chromium on same-site, different-port origins, not proof for every third-party storage partition or physical device.
