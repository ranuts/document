# Gemma 3 1B: loading configuration conflict

The planned seven-language writing run did not execute any Gemma writing cases. The current application attempted the installed SDK catalog ID `gemma3-1b-it-q4f16_1-MLC`, then successfully loaded CPU Qwen as a fallback. The driver deliberately refused to attribute CPU output to Gemma.

A second run captured the actual Worker throw packet: `WindowSizeConfigurationError`, with `context_window_size: 4096` and `sliding_window_size: 512`. This establishes a configuration incompatibility in the attempted integration, not a Gemma writing-quality failure or measured memory shortage. The previously captured catalog entry specifies 4096; the model config specifies positive sliding-window size 512. Installed SDK source merges downloaded config, catalog overrides, then reload chat options.

A separate diagnostic modified Worker reload and non-streaming request chat options to set context window -1 and sliding window 512. That run advanced to `AttentionSinkSizeError`, requiring a nonnegative attention sink value. It also executed zero writing cases and closed the browser context. A further isolated run was declared with attention sink 0 in addition to the window override. Its generation results must be evaluated separately before any adoption decision. These diagnostic overrides are not production source changes, do not change the default model, and do not certify actual memory usage or general artifact compatibility.

The independent verifier checks the preserved failed reports, driver hashes, actual fallback engine, empty writing results, unchanged served bundle and exact Worker configuration errors. Run `python3 docs/evaluations/verify-gemma3-1b-load-conflict.py`. Model quality remains untested in these failed reports. Page request observations do not comprehensively cover Worker network traffic.

## Sliding-window diagnostic terminated with partial writing results

With context -1, sliding window 512 and attention sink 0 supplied via Worker chat options, the actual engine loaded on WebGPU as Gemma. Fifteen cases completed: four edits and eleven refusals. All four edits had exact native Undo/Redo. Their semantic quality was unacceptable: Chinese and English summaries returned only `The inspection is pending.`; Japanese summary returned the instruction `Produce a summary of the text.`; Korean summary invented that Rika proposed inspecting the parking. These passed the existing summary length/numeric guard, showing again that mechanical guards cannot certify factual fidelity. Other raw results invented John/50 euros, changed dates/numbers or returned unrelated English sentences; the preserved refusals left source text unchanged.

The driver terminated before recording case 16 with `Error: Missing native inference`. The report contains 15 rows, no Worker throw packets and unchanged served bundle bytes; the context closed. This assertion establishes incomplete diagnostic coverage, not the reason the following request was absent. No full 21-case accuracy claim is made. The override also changes the attention policy; a short sliding window may itself weaken fidelity. This does not establish the intrinsic quality of Gemma with a different compatible runtime. Do not adopt this diagnostic configuration or change defaults from these results.

Run `python3 docs/evaluations/verify-gemma3-1b-sliding-window-writing.py` to check the partial fixture sequence, exact Worker override/model identity, source payloads, sampling/schema, preserved refusals and native Undo/Redo for the four edits. Native Save, offline restart and measured memory are outside this run.
