# Local initialization recovery

Actual production IM with selected Qwen3 4B was exercised using controlled WebLLM worker-construction failure. The failed candidate was followed by the real cached CPU Qwen3 0.6B runtime, which generated Hello without a new visible error, page error or preview. This validates application fallback, not physical OOM or GPU-device-loss handling.

A second case deliberately failed the first CPU blob-worker construction too. The existing model-load error appeared; the text input remained available for composing. After removing only the CPU failure injection, the existing settings toggle and Load button retried initialization. WebLLM construction failed again; a fresh actual CPU candidate loaded and generated Hello. Counters were two GPU failures and exactly one CPU failure, establishing that successful retry did not merely reuse the original failed candidate. Submitting during the failed state was not checked in this UI probe. No product or UI changes were needed.

The initial WASM-request-abort probe did not intercept any WASM fetch (counter zero), so it timed out while waiting for a load-failure error. Its report remains failed; it is not a CPU failure or recovery result. The worker-construction probe makes injection observable and retains that diagnostic.

Report: 2026-10-03-local-init-recovery-worker-ui.json. Reusable probe: probe-local-init-recovery-worker-ui.mjs, using isolated ai-offline/profile and production preview 5193. CPU model must be cached and that profile must not be used concurrently. Report includes source hash. Local/wllama lifecycle unit tests passed (2 files, 21 tests); root TypeScript lint passed. Physical memory exhaustion, GPU resource cleanup after real allocation, initialization Stop timing and offline failure recovery remain unverified by this scenario. An in-flight generation is never automatically replayed through another engine; the existing lifecycle tests cover that separate invariant.
