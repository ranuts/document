# Narrow IM visual-viewport tracking

Source investigation found the fixed panel used `height: 100dvh` with no visual viewport listener. Short-window layout tests change the layout viewport and therefore do not prove real keyboard visibility. [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport) documents that an on-screen keyboard can shrink the visual viewport while the layout viewport remains unchanged.

The new helper follows visual viewport height and vertical offset for window widths up to 480px at scale 1. Resize and scroll updates set panel-local inline height/top. Desktop, unavailable API, invalid geometry and pinch zoom release overrides to the existing CSS fallback; zoom is not disabled. Listeners are detached on pagehide. A persisted pageshow remounts tracking for a back-forward-cache return. This changes no inference, document operation or preview/confirmation flow.

Regression tests verify synthetic visual viewport resize/scroll, zoom release, restoration, desktop/API fallback and listener disposal. A panel integration test verifies pagehide → persisted pageshow → subsequent viewport resize. The lifecycle test failed before its repair. Independent review identified this lifecycle issue and found no remaining important issues after correction. Final 130 test files / 4,424 tests passed, TypeScript and changed-file oxlint passed, diff whitespace checks passed, and the final production build passed. Existing full-suite asynchronous rejection warnings remain.

These are source and controlled unit/integration results. They are not real browser keyboard events, physical iOS/Android validation, natural back-forward-cache admission or on-device memory acceptance. Actual browser geometry under controlled visual-viewport shrink and physical keyboard behavior still require separate validation. Preexisting sidebar/resize/controller lifecycle on cached page returns was not repaired or accepted by this bounded change.
