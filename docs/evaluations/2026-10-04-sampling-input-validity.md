# Consistent sampling input validity

The generation request validator accepts arbitrary finite temperature values within 0–2 and top_p values strictly greater than zero through one. Previously the HTML input step=0.1 rejected temperature 0.35, and top_p min/step=0.01 rejected 0.005, even though both are valid requests. Sampling fields now use step=any. Top_p min=0 supplies the HTML range boundary; the shared normalizer enforces the exclusive zero boundary. Field-specific customValidity mirrors aria-invalid and uses the localized existing error text. Locale sync also refreshes that text. Token limits retain integer step=1 and the existing 32–1024 range.

A red-first regression test demonstrates native checkValidity rejecting 0.35 before the fix. It now verifies native acceptance of 0.35 and 0.005, forwards both settings, rejects top_p=0 via aria-invalid and customValidity, and retains the last good top_p. Build, all 116 test files / 4201 tests, and lint passed. Independent review found no Important issue.

Actual owned Chromium IM settings recover from an invalid output limit, then accept temperature 0.35 and top_p 0.005. All four input checkValidity values are true. The captured real WebGPU Qwen3-1.7B streaming Worker request contains those exact sampling values and max_tokens 96. The model replies, visible statistics are present, native empty Word text is unchanged, and no page/message errors or preview cards occur. The verifier binds the report to executed driver bytes and checks native validity and outgoing parameters.

This changes validation consistency without adding fields or confirmation. The browser sample uses English UI, a warm profile, network available and service workers blocked. Zero-boundary rejection has unit coverage only in this run. CPU sampling values, actual sampling distribution, screen readers, other locales, cold offline, network privacy and physical devices are not certified. Inherited empty-document Undo/Redo fields are ignored.
