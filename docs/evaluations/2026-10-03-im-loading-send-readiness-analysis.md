# Keep drafts usable while local models reload

An actual CPU Stop probe in the previous change sent the next request before model reinitialization was ready. The existing readiness gate retained the draft and opened settings, but the enabled send button had suggested the request would execute. It did not queue or automatically replay that request.

ChatView now supports a host canSend(text) check for both button availability and Enter submission. Rejection leaves the original draft editable and intact. refreshSendAvailability() updates readiness without submission, and running turns always retain Stop. The panel refreshes availability when loading starts and when runtime state changes, including cancellation, failure and ready transitions. It allows requests if loading is inactive, the engine is already ready, or the existing direct-command parser identifies a native operation outside tools mode. Model-dependent requests remain disabled during unavailable loading. No new control, preview, confirmation or automatic retry was added.

Two regression tests were observed failing before the change. The focused 43-test suite verifies blocked Enter, editable drafts, explicit ready refresh, no queuing, Stop availability, actual panel reload transitions, stable history and closed settings, and direct-command availability. Existing already-ready provider tests also pass: loading bookkeeping alone must not suppress a ready engine. Independent review found no Critical or Important issue. Production build, root lint, and the full 115-file / 4081-test suite passed. Existing converter PromiseRejectionHandledWarning messages predate this change.

The final production probe used actual cached CPU Qwen 0.6B inference and native Workers. Only later Worker instances were held, leaving the initial generation and its cancellation unmodified. After Stop, the first Worker was terminated, a second Worker was constructed, and its initialization postMessage was held (reinitHeld=1). The existing loading status remained visible with settings closed. A draft was editable, Send was disabled, and Enter preserved the exact draft and user-message count. A recognized direct write command enabled Send; this checks its availability, not execution during the hold.

Releasing the real initialization message restored the CPU-ready status and enabled Send without changing the draft or adding a user turn. Manual Send then produced “Hello.” No page or visible errors or preview cards were recorded. The screenshot was visually inspected and retains the existing restrained IM layout. Exact executed probe sources and SHA-256 hashes accompany reports. The initial broader hold also passed UI checks, but could intercept existing-generation messages; it is retained as diagnostic evidence rather than the final reinitialization proof.

This is desktop Chromium with cached models and a controlled initialization-message hold. It does not establish physical mobile keyboard behavior, physical OOM recovery, download stalls, or native document execution during the hold. Model-unavailable states after loading failure retain the existing explicit retry/configuration behavior.
