# Current browser runtime handover UI

Actual native Word IM loaded the current build's Qwen3 0.6B automatic CPU fallback. Only GPU availability was forced off; model inference and native runtime were real. A diagnostic wrapper delayed the first SDK `exit()` call before invoking its unchanged original implementation, making the waiting interval controllable. No response, provider result or document operation was substituted.

The visible model selector's change event reset the current provider. Clicking its visible Load button entered preparation before old exit completed: status “正在准备 AI…”, indeterminate progress visible, Stop visible, Load disabled, one pending native exit and zero replacement loads. Clicking Stop restored enabled loading controls and hid progress. Releasing the diagnostic gate allowed original native exit to finish once; no replacement load started, and “已停止。” stayed visible.

A new explicit Load then invoked the real CPU model loader once and reached readiness. Sending “你好” produced one actual assistant answer without error guidance or preview cards. The native Word content remained exactly the initial empty paragraph. This is recovery availability, not answer-quality acceptance or Word edit/history evidence.

The on-disk bundle stayed unchanged. Browser context closed in finally, and the corrected probe exited 0.

The [first attempt](2026-10-05-runtime-handover-ui-before.json) and its [exact driver copy](probe-runtime-handover-ui-before.mjs) remain preserved. It timed out before validating waiting/Stop/recovery; no product failure is inferred. Correction used the current visible model/Load/Stop controls and their normal change/click handlers. No direct-GGUF handover acceptance is claimed by the corrected run.

Scope: current desktop Chromium native IM with controlled exit delay and warmed model cache. It does not exercise naturally slow/failing native teardown, physical OOM/GPU loss, direct-GGUF mode, offline or installed PWA, mobile, deployed headers, Save/reopen or semantic model quality. The model selector was reset through its normal change handler with its existing value; this is provider reload/handover testing, not a different-model quality comparison.
