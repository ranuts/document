# Return keyboard focus after closing IM — 2026-10-04

Previously, activating the focused Close button hid the panel and left Chromium's parent active element on body. The first subsequent Tab also remained outside the editor frame, rather than returning to a visible native control. The synthetic Word reproduction is retained as the before JSON; it has no intrinsic driver hash and is not broader multi-editor baseline evidence.

The panel now captures whether focus is inside it before hiding. Only that case returns focus to the existing native AI rail entry. If the rail is unavailable, the editor iframe receives focus. Programmatic closes from external controls keep their existing focus. A pending open-focus microtask already checks the current open state, so closing does not later focus hidden input. The implementation calls no document content or selection API; IM draft retention is checked in the browser matrix.

The native rail moves between left/right with compact chrome. Reparenting now restores its focus only when its owner document actually has focus and its active element is the button. Independent review identified why a remembered iframe activeElement alone can steal parent composer focus. The focused-call regression failed for that original condition; the hasFocus ownership check resolves it. jsdom does not accurately model cross-frame focus ownership, so that regression explicitly supplies the unfocused iframe state and verifies no focus call. The native editor browser matrix did not reproduce that secondary steal before the guard; do not claim every browser did so.
