# Self-hosted CPU model: actual full download and chat

Current built native Word IM explicitly selected wllama, configured a separate localhost origin serving /model.gguf, and loaded the real pinned Qwen3-0.6B Q4_K_M artifact. The artifact was downloaded to a task-owned temporary file from the exact revision URL used in local.ts, then served with CORS and HTTP range support. This is a custom localhost origin, not an external deployment or malicious-source test.

Authoritative server capture records a HEAD and a GET. GET transferred the complete 484220320 bytes; both requests had zero request-body bytes. Page request capture also observed the custom-origin GET, no request body and no synthetic chat marker in decoded URLs. The model URL used a new ephemeral server origin, so this model-source key required an actual transfer rather than merely reporting a cached model as downloaded. App/runtime caches were warm; no assertion of a wholly empty browser cache.

The visible engine became CPU · model.gguf, selected provider remained wllama, and actual inference returned text/statistics. Source document stayed unchanged, no previews or page errors. Reply was irrelevant editor-scope wording, so useful answer quality remains unaccepted. Browser and local server closed; temporary downloaded model is retained outside the repository. No product code changed.

Two harness mistakes are preserved: a selector searched for an internal native input that the custom element does not expose; then the probe tried a hidden GGUF load control while the default automatic provider was still selected. The second failed harness did transfer the model but did not complete acceptance. Final probe explicitly selects wllama through the actual component value/change interface before loading. This is programmatic component interaction, not a full keyboard accessibility test.

The report's inherited scope text describes the earlier warm CPU network probe; this analysis clarifies the new evidence: a fresh custom source key and full model transfer. It does not prove HTTPS deployment, CDN redirects, range-resume recovery, physical cold-device memory, every content-bearing header/request outside the page or restrictive deployed CSP. HTTP/HTTPS custom sources are a real supported use case; narrowing Worker permissions to only a fixed CDN would break it.
