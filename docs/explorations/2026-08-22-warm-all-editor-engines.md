# 空闲时预热全部三个编辑器引擎——以及我上一轮算错的那个数

日期：2026-08-22
分支：`perf/warm-all-engines`
起因：上一个 PR 收尾时我写下"自动预取格式特定引擎（每种 ~20 MB，三种 50 MB+）——那是拿访客
流量赌他会打开文档"，用户回：这个也在空闲的时候加载上吧。

## 先更正：那个 50 MB 是错的

我拿**磁盘大小**当成了**流量**。这些引擎是 JS 文本，线上走 gzip/brotli：

|                      | 未压缩   | **gzip（真实流量）** |
| -------------------- | -------- | -------------------- |
| core（上一轮已预热） | 13.57 MB | 10.64 MB             |
| docx 引擎            | 18.79 MB | **3.92 MB**          |
| xlsx 引擎            | 20.52 MB | **4.29 MB**          |
| pptx 引擎            | 18.04 MB | **3.74 MB**          |
| 合计                 | 70.91 MB | **22.58 MB**         |

三个引擎加起来是 **11.95 MB**，不是 57 MB。压缩比接近 5:1，因为
`sdk-all.js` 那 13.67 MB 是纯文本。

所以"拿访客流量赌"这个判断建立在一个错了 5 倍的数字上。用户的要求本来就是对的。
**教训：谈流量必须量压缩后的大小，`stat` 出来的数字不是访客付的账。**

## 改动

`warmEverything()` = core → docx → xlsx → pptx，全程串行，每一段各自等一个 idle 时刻
（页面在忙就不排队占着）。顺序按打开频率，被点击打断时已完成的部分最可能正是要用的那个。

加了存储配额检查：`navigator.storage.estimate()`，剩余空间不足以放下约 120 MB（未压缩
落盘 + 按需字体的余量）就整个不做。Cache.put 失败早已被 worker 吞掉、不会出错，但那意味着
花了访客的流量换一堆立刻被驱逐的字节——不如不花。API 不可用时视为有空间（不能因为拿不到
证据就把功能关掉）。

hover 层保留：它现在的作用是把某个格式**插到队列前面**，而不是等它排到。

## 收益（gzip 开启，冷基线关闭了预热）

| 格式 | 冷访客            | 预热后            | 节省     |
| ---- | ----------------- | ----------------- | -------- |
| docx | 13.83 MB / 74 req | 7.56 MB / 63 req  | **−45%** |
| xlsx | 9.27 MB / 60 req  | 2.63 MB / 49 req  | **−72%** |
| pptx | 24.46 MB / 75 req | 18.36 MB / 64 req | **−25%** |

预热本身 1.3 秒跑完 20 个文件（本地）。首页 FCP 不受影响（idle + 串行 + 低优先级）。

## 剩下的几乎全是字体

对照上一轮量的格式字体体积，剩余字节几乎完全对得上：

| 格式 | 打开后仍需下载 | 该格式的字体 catalog |
| ---- | -------------- | -------------------- |
| docx | 7.56 MB        | 7.49 MB              |
| xlsx | 2.63 MB        | 2.52 MB              |
| pptx | 18.36 MB       | 18.22 MB             |

**引擎已经全部命中，剩下的就是字体。** 要再往下压，唯一的大块就是格式特定的字体
（三种合计 28.23 MB，且是二进制、压不动）。这一步没有做：它是上面这一步的三倍体积，
而且 catalog 索引会随 vendor 升级重新编号。是否值得，交给决策而不是我替用户决定。

## 两个把我骗过去的测量陷阱

**第一次的结果是 docx `-0%`**，cold 和 warmed 连请求数都一模一样。查下去发现：
**冷基线是被污染的**——cold 那一轮页面自己也在跑后台预热，600 ms 内已经把排在最前面的
docx 引擎缓存了，只是那些下载发生在计量开始之前，白白算进了"冷"访客的免费额度。
排在最后的 pptx 没轮到，所以只有它显出差异。

修法：冷基线用 `addInitScript` 伪造 `navigator.connection.saveData = true`，让页面**主动
拒绝**预热。顺带这也验证了门槛逻辑本身。

**第二个陷阱在上一轮就存在**：`page.waitForFunction(async () => ...)` 对 async predicate
不可靠（返回的 Promise 本身 truthy），它一直在报告"预热完成"。这次全部改成
`page.evaluate` 直接 await 暴露出来的函数。

两次都是同一类错误：**测量脚本比被测代码更容易出错，而它出错时给出的是一个看起来合理的
数字。** 上一个 PR 报的 34.12 → 29.60 MB 同样受这两个问题影响（且是未压缩口径），真实收益
比当时写的更大。

## 用例

`test/e2e/landing-prefetch.spec.ts` 新增一条：core 之外，**三个编辑器的引擎全部进入 SW
cache**，断言总数是 8 + 3×4。原有那条"预热后打开不走网络"也扩展到覆盖 docx 引擎文件。

反向验证：把 `warmEverything` 砍回只有 CORE → 新用例列出 13 个未缓存文件后变红；
让配额判定恒为 false → 后台层用例变红。

## CI 抓出来的竞态：cache.put 活不过 respondWith

本地全绿，CI 的 `E2E shard 2` 红在 `/sdkjs/slide/sdk-all.js` 没被缓存——**队列里的最后
一个文件**。

根因不在测试：`respondWith` 在响应交到页面手里的那一刻就算完成，此时 worker 如果没有别的
待办事项，浏览器**可以立刻终止它**——正在写的 `cache.put` 就跟着没了。文件越大窗口越宽，
而这正好是反的：13.7 MB 的 SDK 恰恰是最值得留住的那个。本地看不见，因为没有任何东西在催
worker 关闭。

所以修的是 `public/sw.js`：所有缓存写入都包进 `event.waitUntil(...)`。一共四处——
vendor 的 cache-first、stale-while-revalidate，以及 network-first 分支里那两处
CORE_CACHE 写入（HTML 更小，但失败模式一模一样）。

**这是生产环境的正确性修复，不只是让测试变绿。**

测试那一侧也确实有问题，一并修了：页面侧的 Promise 在读完最后一个响应时就 resolve，而
worker 的 put 在它自己那边稍后完成。要求两者同一瞬间就位是断言的错，不是功能的错——
改成 `expect.poll` 等最终一致。

`waitUntil` 本身很难用运行时用例守护（要可靠地触发"worker 被终止"）。改用源码契约钉住，
和仓库里 `landing-pages` / `workflow-contract` 的做法一致：
`putInRuntimeCache` 的每个调用点都必须在 `event.waitUntil(` 里，fetch handler 里的每处
`caches.open(CORE_CACHE)` 前面都必须紧跟 `event.waitUntil(`。反向验证：任意一处退回裸调用
都会变红。

（中途我还写了第三条"禁止裸 put"的断言，但它的正则分不出 put 有没有被 waitUntil 包着——
删掉了，前两条已经精确覆盖。宁可少一条断言，也不要一条说不清自己在测什么的。）
