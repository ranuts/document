# 发现：文档含图片时保存永久卡死（线上复现）+ 验证方法缺口

日期：2026-08-15
线上：https://edit.chaxus.com/ （v9，`a4a58d5` 之后）
起因：用户追问"已关闭的 issue 是否都验证过了，怕问题重新出现"，以及
"为什么只验证 embed-demo，常用的是直接在网页上打开编辑"。两个质疑都
成立，顺着查出了一个**真实的、可复现的线上 bug**。

## 一、验证方法的缺口（用户指出，属实）

此前所有线上验证都经 `embed-demo.html` 的 `post()` 接口驱动，原因是它
可编程、能自动化；但代价是**只覆盖了 embed 这条代码路径**
（postMessage → `embed-api.ts`），而主站走的是另一条
（`lib/ui.ts` / `lib/document.ts` / 文件选择 / `saveFileToDisk`）。
尤其保存：embed 模式下本地保存是被**禁用**的
（`routeSavedFile` 里 `isEmbedMode()` 直接 return），所以主站真正的
保存 UX 一次都没被验证过。

**补救方法**：主站的 `?src=` 参数可自动化（也是真实用户流程 + 外部
链接在用）。本轮已用它验证主站：

- ✅ `?src=` 打开远程 docx，渲染正确；
- ✅ 键盘编辑生效（输入 "EDIT" 正常渲染）；
- ❌ 含图片保存——见下。

**结论固化**：以后声称"线上已验证"必须区分 embed 路径与主站路径；
embed-demo 通过不等于主站通过。

## 二、已关闭 issue 的验证强度分级（诚实盘点）

| 强度             | issue                        | 说明                           |
| ---------------- | ---------------------------- | ------------------------------ |
| E2E 永久守护     | #113 #31 #28 #13 #33 #25 #87 | CI 每次跑，回归会立刻失败      |
| 线上人工实测一次 | #49 #21 #12 #92 #64 #15      | 无自动化守护，可能静默回归     |
| 仅靠推理 + 单测  | #72                          | 本轮复验，**发现问题**（见三） |
| 功能诉求         | #22 #6                       | 升级本身即满足                 |

即：**只有 7 个有永久守护**，6 个是一次性人工验证。这正是用户担心的
"问题重新出现"的暴露面。

## 三、新发现的 bug：文档含图片时保存永久卡死

**复现步骤**（4 次复现，2 条路径）：

1. 打开任意 docx（主站 `?src=` 或 embed `document:open-buffer` 均可）；
2. 经 SDK 的 `AddImageUrlAction(url)` 插入一张网络图片——图片能正确
   下载并渲染到文档里（截图确认，红色方块可见、带选中控制点）；
3. 触发保存（embed 的 `document:save`，或主站的
   `asc_DownloadAs(new Asc.asc_CDownloadOptions(65))`）；
4. **页面主线程永久阻塞**：CDP 的 `Runtime.evaluate` 全部超时，
   截图也超时；最久观察超过 12 分钟仍未恢复，无控制台错误输出。

**对照实验**：同一份 docx **不插图**直接保存 → 3.1 秒完成、产物 25KB
正常 zip。所以卡死与图片直接相关，不是保存链路整体坏了。

**排除的干扰因素**：

- 不是 localhost 图片的问题：换成同源 https 图片
  （`https://edit.chaxus.com/img/64.png`）同样卡死；
- 不是 embed 特有：主站 `?src=` 路径同样卡死；
- 不是"慢"：12 分钟未完成，且主线程完全阻塞（同步卡死特征）。

**尚未确认（重要，别过度断言）**：

- 插图用的是 SDK 的 `AddImageUrlAction`（我们旧 patch 时代就用它，是
  稳定别名）。**UI 路径（Insert → Image → Image from URL 对话框）没能
  自动化验证**——对话框输入框对合成 input 事件不认（红色校验感叹号），
  属于既有的工具限制，不是产品问题。因此需要**真人用鼠标走一遍 UI**
  确认 UI 路径是否同样卡死。
- 本地文件插图（Image from file）未测（文件选择器无法自动化）。
- 粘贴图片（#72 原始报障场景）未测（剪贴板无法自动化）。

**与 #72 的关系**：#72 是"复制进来的图片保存时报错 + 插入在线 url 图片
不显示"。现在"插入 url 图片不显示"这半**已修复**（图片正常渲染），
但"图片 + 保存"这半在新引擎上表现为**卡死**而不是报错。属于同一用户
场景，因此 #72 的关闭需要重新审视（待人工 UI 复核后决定 reopen 还是
另开新 issue）。

**优先级判断**：这是**用户可感知的严重问题**——文档里有图片就存不出来，
且没有任何错误提示，页面直接假死。应排在下一阶段规划所有内容/SEO 项
之前。

## 四、由此产生的行动项

1. **人工 UI 复核**（真人鼠标）：Insert → Image from URL / from file →
   保存，确认是否复现；若复现则 reopen #72 或另开 issue。
2. **定位根因**：怀疑方向——保存时媒体序列化路径（`writeMediaFiles` /
   x2t 媒体合并）在图片存在时进入同步死循环；从编辑器 iframe 内的
   `onlyoffice-file-stream` 是否发出可判断卡在编辑器内还是页面侧。
3. **补 E2E 守护**：这个场景必须进回归套件（插图 → 保存 → 校验产物
   含 media 条目），否则修好也会再回归。
4. **给一次性人工验证的 issue 补自动化**：#49（.doc 打开）、#21（批注
   API）成本低，值得进 E2E；#12/#92/#64（光标与渲染）可用
   `cursorPos` + `#ce-cursor` 这类可断言状态覆盖。
