# 一次自动保存快照到底多贵：实测与自适应间隔

日期：2026-08-22
分支：`perf/measure-export-cost`
前情：[自动保存与本地历史实施记录](./2026-08-22-autosave-history-implementation.md)

## 起点：90 秒是拍脑袋拍出来的

一期落地时，快照间隔写死 90 秒，理由只有一句"导出很贵"——贵到什么程度没人量过。
评估文档里我自己把"量导出成本"列为一期最该先做的事，然后没做。

## 测出来的数字

新增 `bin/export-benchmark.mjs`（只读，经 embed API 打开文档并导出，页面内合成 fixture，
不落盘）。桌面、本地 preview、x2t 已加载：

| 文档           | 打开   | 首次导出 | 热导出     | 快照体积 |
| -------------- | ------ | -------- | ---------- | -------- |
| docx，1 段     | 168 ms | 1172 ms  | **42 ms**  | 25 KB    |
| docx，200 段   | 160 ms | 1134 ms  | **51 ms**  | 25 KB    |
| docx，2000 段  | 161 ms | 1215 ms  | **87 ms**  | 31 KB    |
| xlsx，1000 行  | 161 ms | 1115 ms  | **59 ms**  | 33 KB    |
| xlsx，20000 行 | 164 ms | 1378 ms  | **123 ms** | 486 KB   |

两个结论：

1. **首次导出约 1.2 秒，之后是几十毫秒。** 那 1.2 秒是加载 x2t 的一次性成本，
   而且它由用户的第一次保存承担，不由快照承担——除非快照恰好是这个会话的第一次导出。
2. **热导出比预估低一个数量级。** 90 秒的间隔在桌面上过于保守：按 42~123 ms 算，
   一次快照占用的时间还不到一帧半到八帧。

## 但 90 秒不能简单改成 30 秒

同一个数字在手机上是另一回事：同样的导出会慢几倍，而那台设备本来就离
"canvas 被回收"（#145）更近。**一个固定值不可能对两端都对。**

所以改成按**占空比**推导：让导出时间占运行时间的固定比例 1/300（0.33%）。

```
interval = clamp(lastExportMs × 300, 30s, 180s)
```

- 42 ms → 12.6 s → 取下限 **30 s**
- 123 ms → **36.9 s**（下限没起作用，占空比自己算出来的）
- 600 ms（慢手机）→ **180 s**（取上限，主动退让）
- 还没测过时（会话第一次）→ **60 s**

设备通过"跑得快还是慢"自己决定间隔，不需要任何设备探测、UA 判断或
`deviceMemory` 猜测。这也是这条规则真正的好处：它对将来更慢或更快的设备同样成立。

## 顺带修的一处测试脆弱性

`autosave-recovery.spec.ts` 里"编辑→隐藏页面→快照"的等待窗口原本是 45 秒，
是按 90 秒间隔选的。间隔下限变成 30 秒之后，45 秒的窗口会让**周期性 tick 也来得及**，
用例就又变回"无论 hidden 分支在不在都绿"。窗口收到 25 秒（严格小于任何可能的间隔），
并反向验证过：摘掉 hidden 快照，该用例变红。

## 还没答的

- 真机移动端的热导出到底多少毫秒（这里只有桌面数字，占空比规则是为它设计的，但没验证过）。
- 含图片/复杂样式的真实文档比合成 fixture 重多少（`bin/corpus-report.mjs` 的
  `save p50/p95` 一栏能给，需要本地语料）。
- `bin/export-benchmark.mjs` 目前不测内存峰值；x2t 的 283 MB 是常驻的，
  但导出期间的额外峰值没量。
