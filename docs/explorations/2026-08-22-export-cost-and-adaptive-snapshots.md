# 一次自动保存快照到底多贵：实测与自适应间隔

日期：2026-08-22
分支：`perf/measure-export-cost`
前情：[自动保存与本地历史实施记录](./2026-08-22-autosave-history-implementation.md)

## 起点：90 秒是拍脑袋拍出来的

一期落地时，快照间隔写死 90 秒，理由只有一句"导出很贵"——贵到什么程度没人量过。
评估文档里我自己把"量导出成本"列为一期最该先做的事，然后没做。

## 测出来的数字

新增 `bin/export-benchmark.mjs`（只读，经 embed API 打开文档并导出，页面内合成 fixture，
不落盘）。桌面、本地 preview、x2t 已加载：

| 文档           | 打开   | 首次导出 | 热导出     | 快照体积 |
| -------------- | ------ | -------- | ---------- | -------- |
| docx，1 段     | 168 ms | 1172 ms  | **42 ms**  | 25 KB    |
| docx，200 段   | 160 ms | 1134 ms  | **51 ms**  | 25 KB    |
| docx，2000 段  | 161 ms | 1215 ms  | **87 ms**  | 31 KB    |
| xlsx，1000 行  | 161 ms | 1115 ms  | **59 ms**  | 33 KB    |
| xlsx，20000 行 | 164 ms | 1378 ms  | **123 ms** | 486 KB   |

两个结论：

1. **首次导出约 1.2 秒，之后是几十毫秒。** 那 1.2 秒是加载 x2t 的一次性成本，
   而且它由用户的第一次保存承担，不由快照承担——除非快照恰好是这个会话的第一次导出。
2. **热导出比预估低一个数量级。** 90 秒的间隔在桌面上过于保守：按 42~123 ms 算，
   一次快照占用的时间还不到一帧半到八帧。

## 但 90 秒不能简单改成 30 秒

同一个数字在手机上是另一回事：同样的导出会慢几倍，而那台设备本来就离
"canvas 被回收"（#145）更近。**一个固定值不可能对两端都对。**

所以改成按**占空比**推导：让导出时间占运行时间的固定比例 1/300（0.33%）。

```
interval = clamp(lastExportMs × 300, 30s, 180s)
```

- 42 ms → 12.6 s → 取下限 **30 s**
- 123 ms → **36.9 s**（下限没起作用，占空比自己算出来的）
- 600 ms（慢手机）→ **180 s**（取上限，主动退让）
- 还没测过时（会话第一次）→ **60 s**

设备通过"跑得快还是慢"自己决定间隔，不需要任何设备探测、UA 判断或
`deviceMemory` 猜测。这也是这条规则真正的好处：它对将来更慢或更快的设备同样成立。

## 顺带修的一处测试脆弱性

`autosave-recovery.spec.ts` 里"编辑→隐藏页面→快照"的等待窗口原本是 45 秒，
是按 90 秒间隔选的。间隔下限变成 30 秒之后，45 秒的窗口会让**周期性 tick 也来得及**，
用例就又变回"无论 hidden 分支在不在都绿"。窗口收到 25 秒（严格小于任何可能的间隔），
并反向验证过：摘掉 hidden 快照，该用例变红。

## 慢设备上真的会退让吗：CPU 节流实测

占空比规则是**为慢设备设计**的，而上面的数字全部来自桌面。用 DevTools 协议的
`Emulation.setCPUThrottlingRate` 把 CPU 按倍数降速（4x/6x 是中端/低端手机的常用替身），
`bin/export-benchmark.mjs` 现在支持第三个参数：

| 文档           | 桌面 1x           | 中端 4x            | 低端 6x                    |
| -------------- | ----------------- | ------------------ | -------------------------- |
| docx，1 段     | 40 ms → **30 s**  | 197 ms → **59 s**  | 335 ms → **101 s**         |
| docx，200 段   | 49 ms → **30 s**  | 181 ms → **54 s**  | 316 ms → **95 s**          |
| docx，2000 段  | 87 ms → **30 s**  | 315 ms → **95 s**  | 495 ms → **149 s**         |
| xlsx，1000 行  | 50 ms → **30 s**  | 214 ms → **64 s**  | 299 ms → **90 s**          |
| xlsx，20000 行 | 141 ms → **42 s** | 573 ms → **172 s** | 896 ms → **180 s**（上限） |

规则按设计工作，而且退让是**连续的**而不是台阶式的：同一台设备上，文档越重间隔越长；
同一份文档，设备越慢间隔越长。低端手机上的两万行表格直接顶到 180 秒上限。

两点值得记住：

- **最坏情况丢多少**：低端手机上小文档约 100 秒、大表格 180 秒。对照 Office AutoRecover
  默认 10 分钟，这仍然是更紧的窗口。
- **单次卡顿多久**：6x 下两万行表格一次导出 896 ms，接近一秒的主线程阻塞，手机上能感觉到。
  但占空比把它摊成"每 3 分钟一次"，全程占用仍是 0.33%。这正是选占空比而不是固定间隔的理由：
  **卡顿的绝对时长由设备决定，卡顿的占比由我们决定。**

## 这些代码在编辑器首屏上要多少体积

自动保存的存储层被 `lib/document.ts` 静态导入，所以它在编辑器的关键路径上。量了两次：

- `/history` 页面是**独立入口**，23.18 kB（gzip 6.68 kB）+ 7.43 kB CSS，不进编辑器 ✓
- 存储层本身：把 `startDocumentSession` 的调用与 import 摘掉重新构建，所有 JS chunk 的
  gzip 总和从 2 386 060 变成 2 386 834 字节——**"移除后反而大了 774 字节"**，也就是说
  它的贡献已经落在 chunk 拆分抖动的噪声里了。

这个测法本身有局限（总量里绝大部分是 vendor 与 ranui，几 KB 的差异被淹没），但结论方向
是明确的：存储层在 gzip 后是**几 KB 量级**，不值得为它引入异步边界去懒加载。真要精确到
字节，需要按 `editor.html` 的实际 chunk 图去算，那笔账等到首屏预算真的紧张时再记。

## 还没答的

  节流只降 CPU，不模拟手机的内存压力、更慢的存储与 GPU，而 x2t 的 283 MB 恰恰是内存问题。
- 含图片/复杂样式的真实文档比合成 fixture 重多少（`bin/corpus-report.mjs` 的
  `save p50/p95` 一栏能给，需要本地语料）。
- `bin/export-benchmark.mjs` 目前不测内存峰值；x2t 的 283 MB 是常驻的，
  但导出期间的额外峰值没量。
